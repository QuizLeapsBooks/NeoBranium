| Question | Verified finding | Relevant file/function | Implementation implication |
|---|---|---|---|
| NeoBook identity mapping | `getClientIdentity` uses `req.uid` (set only after bearer-token verification) to form `uid_${uid}` and stores that UID. Missing/invalid auth falls back to `ip_${HMAC(normalized IP)}` with `uid: null` and `isGuest: true`. Current authenticated records are directly mappable when both stored `uid` and `identityKey` match. Guest/IP records cannot be safely linked to a later account; do not infer ownership by IP. Usage documents store UID/identity/guest fields, but reservations store only identity key/date. Current config sets 30-day usage expiry; actual deployed TTL behavior and old data were not inspected. | `services/neobookLimitService.js`: `getClientIdentity`, `checkAndConsumeNewChatQuota`, `recordMessageTokenUsage`, `reserveTokenUsage`; `routes/neobookRoutes.js`: `attachIdentity` | Include historical totals only where `uid === verified UID` and `identityKey === uid_${verified UID}`; exclude guest, missing, or mismatched identities. Do not expose reservation documents as user history. |
| NeoBook feature attribution | `neobook_usage` stores combined token/cost totals and counters, with no feature field; token reservations also have no feature. Chat assistant messages persist `tokenUsage`; quiz artifacts persist `tokenUsage`. Flashcard sets and study-guide documents omit it; mind-map generation returns usage but the saved map omits it. Audio episodes save Gemini script token usage and segment byte counts, but not TTS usage/duration. Artifact collections distinguish artifact types, but cannot reconcile every artifact to daily aggregate totals; `messagesCount` is incremented by both chat and reservation settlement and is not a reliable chat-only count. | `services/neobookLimitService.js`: `recordMessageTokenUsage`, `settleTokenReservation`; `routes/neobookRoutes.js`: chat message writes, quiz/flashcard/study-guide/mind-map routes; `services/neobookQuizService.js`, `services/neobookFlashcardService.js`, `services/neobookStudyGuideService.js`, `services/neobookMindMapService.js`, `services/neobookAudioService.js` | Historical feature totals are incomplete; label existing totals “NeoBook / unclassified” except for independently displayed persisted records. For new usage, add feature attribution to NeoBook’s existing accounting flow and persist operation usage as needed; do not mirror NeoBook charges into the central event ledger. |

Label these as operational metrics, not provider-billed units; leave unavailable duration/billing fields null. |

1. **Is the architecture ready for Phase 2?** Yes, conditionally: the current UID mapping and provider parsing patterns are clear. Keep historical NeoBook attribution limited to verified UID-matching data and treat its feature split as unclassified.
2. **Exact decisions to finalize before coding:** (a) enforce the historical inclusion rule `uid` and `identityKey` must both match the authenticated UID; exclude guest/IP and malformed records; (b) preserve NeoBook’s existing ledger as its only accounting source, extend future writes with feature attribution, and do not duplicate NeoBook events in the central ledger; (c) define separate provider/estimated/unavailable token sources, with totals derived from input + output unless provider total is explicitly captured; (d) settle typed observable image/audio metrics without claiming provider-billed units.
3. **Remaining uncertainty:** deployed Firestore TTL configuration and contents of historical documents; availability of provider-reported image/audio billing metrics; production model/provider overrides. This source review cannot verify live data or deployed behavior.
